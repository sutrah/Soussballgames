# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, no-build, no-account website of camera-controlled mini-games ("Soussballgames"). Every game runs entirely in the browser: pose/hand tracking via MediaPipe Tasks Vision (loaded from CDN at runtime), no backend, no login. Plain HTML/CSS/vanilla ES modules — no `package.json`, no bundler, no framework, no test runner.

## Commands

- **Run locally**: `python3 -m http.server 8080` from the repo root, then open `http://localhost:8080`. A `SessionStart` hook (`.claude/settings.json`) already does this automatically for interactive sessions — check `http://localhost:8080` before starting a second server.
- **Syntax-check a JS file**: `node --check path/to/file.js` (parses only, never executes — safe, and pre-approved in `.claude/settings.json`). A `PostToolUse` hook runs this automatically on every `.js` file Claude writes or edits and reports errors back inline.
- There is no linter, formatter, or automated test suite configured. CI (`.github/workflows/ci.yml`) only runs `node --check` over every `.js` file on push/PR.
- Pushing to `main` or `claude/sleepy-pascal-rxsu3g` auto-deploys the site to GitHub Pages (`.github/workflows/deploy-pages.yml`) — requires "Pages → Source: GitHub Actions" enabled once in repo settings. **As of the last check, every single run of this workflow has failed** (fails specifically at the `actions/deploy-pages@v4` step, not the build) and `https://sutrah.github.io/Soussballgames/` 404s entirely — this is a repo-settings issue, not a code bug, and it's site-wide (every game 404s, not just a newly-added one). If a user reports a game "won't launch" or "impossible de lancer", check `mcp__github__actions_list` (`list_workflow_runs` on `deploy-pages.yml`) and curl the live URL *before* assuming a code regression — this has been the actual cause at least once. The fix is for a repo admin to enable Pages → Source: GitHub Actions in the GitHub UI; it can't be fixed by pushing a commit.

### Testing a game without a real camera

Games require `getUserMedia` + MediaPipe pose detection, so they can't be smoke-tested by just loading the page. The working pattern used throughout this repo's history:

1. Serve the repo (see above).
2. Drive it with Playwright + a **fake camera**: launch Chromium with `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream` (and `--ignore-certificate-errors`, since MediaPipe/PeerJS CDN assets go through this environment's TLS-intercepting proxy). The fake device is a synthetic pattern with no real body in it, so `PoseController` will report `null` landmarks — enough to test UI flow, camera activation, and "no input" states, but not gesture-driven scoring.
3. To verify actual gesture/physics logic (scoring, state machines, level progression) without a real body, temporarily add a `?debug=1`-gated `window.__debugXxx` hook at the bottom of the game's `.js` file that exposes internal state and lets a test script inject synthetic gesture values directly (bypass `PoseController` entirely). **Remove the hook before committing** — it's scaffolding, not a shipped feature.
4. **Known environment quirk, not a game bug**: in this sandbox, MediaPipe falls back to software WebGL (no real GPU), which can make `requestAnimationFrame` run far slower than wall-clock time. Game loops here clamp `dt` per frame (`Math.min(0.033, ...)`), so under this slowdown *simulated game-time* runs in slow motion relative to real seconds. Don't re-diagnose this as a physics bug — it doesn't happen for real users with real GPUs/cameras. When timing matters for a test, drive the game via the `?debug=1` hook (module-level `t`/state, not wall-clock waits) rather than trying to time real camera-frame cadence.
5. Backgrounding a long-lived process (e.g. a test HTTP server) via a Bash tool call only survives if started as `(cmd &)` at the top level of the command — piping it through a nested `bash -c` or `setsid`/`disown` gets reaped when the tool call returns, in this sandbox specifically.

## Architecture

### Shared modules (`assets/js/`)

- **`pose/PoseController.js`** — wraps `getUserMedia` + MediaPipe `PoseLandmarker` (loaded from `cdn.jsdelivr.net`, GPU delegate). Exposes `onFrame(lm, now)` with 33 landmarks, already mirrored (`x' = 1 - x`) so gestures map naturally to what the user sees of themselves. `LM` exports named landmark indices.
- **`pose/gestures.js`** — reusable signal-processing primitives built on raw landmarks: `EMA`/`Baseline` (smoothing/adaptive baseline), `EdgeTrigger` (hysteresis-based rising-edge detector used for step/jump/push detection), plus higher-level one-shot gestures (`handsRaised`, `armsSpread`, `lateralZone`, `shoulderTilt`, `kneeLift`, `elbowExtension`). New games should extend this file rather than re-deriving detection math inline.
- **`pose/skeleton.js`** — draws the small calibration skeleton shown in every game's camera-preview thumbnail.
- **`render/perspective.js`** — shared pseudo-3D "road scrolling toward the camera" projection (`scaleAt`/`yAt`/`xAt` from a `z∈[0,1]` depth), used by the runner game's ground/lane math.
- **`net/PeerRoom.js`** — WebRTC P2P wrapper over PeerJS's public broker (signaling only; gameplay data flows peer-to-peer). No server to host, matches the "no account, no backend" constraint. Star topology: `host(maxPlayers)` accepts up to `maxPlayers - 1` incoming guest connections and assigns each an incrementing seat number (host is always seat 0); `join(code)` connects a guest only to the host, never peer-to-peer between guests. `send(msg)` broadcasts to every connection; `onMessage(cb)` delivers `(msg, fromSeat)`; `onRoster(cb)`/`onStatus(cb)` report connection-list and connection-state changes. **Caveat**: this sandbox's proxy blocks the WebSocket handshake to `0.peerjs.com` (likely datacenter-IP blocking on the free broker's side), so live multi-peer connection can't be verified from inside this environment — only the post-connection game logic can be (see the room game's approach below).

Every game so far draws to a 2D `<canvas>` — `patinage` is the one exception, using **Three.js** (`three@0.160.0`, loaded from `cdn.jsdelivr.net` as an ES module, same CDN-at-runtime pattern as MediaPipe/PeerJS) for real WebGL 3D. If a request explicitly names a 3D engine that isn't a browser library (Ursina, Godot, Unity, Panda3D...), it can't run inside this site's architecture (static HTML deployed to GitHub Pages, no build step, no server) — Three.js loaded from CDN is the fitting substitute, not a compromise to route around silently; say so plainly rather than picking one without a word.

### Per-game structure (`games/<name>/`)

Each game is `index.html` (UI shell: start overlay with instructions, game-over/summary overlay, small camera-preview thumbnail, HUD) + one `<name>.js` module. All follow the same loop shape:

1. `PoseController.onFrame(lm)` updates module-level gesture state (booleans/floats) from live landmarks — kept minimal and cheap since it fires every camera frame.
2. A single `requestAnimationFrame` loop calls `update(dt)` (physics/state advance, reading the gesture state above) then draws to a `<canvas>`.
3. A keyboard (or mouse, for `climb`) fallback path sets the same gesture state variables, so games are testable/playable without a working camera.

Notable per-game specifics:
- **`flappy`** — control is two floor "tiles" (left/right halves of the frame, detected via ankle position) alternately lit by a fixed-tempo metronome, *not* a knee-lift gesture. This mirrors the proven "Pas de Patineur" exercise in the sibling reference repo `sutrah/weballgames` (`squelette.html`), which uses exactly this zone+metronome approach — check that file first before changing this game's input model. Successfully stepping on the lit tile advances the metronome target (`advanceBeat()`); missing it also advances (never stalls). Has an intro countdown and pauses entirely while feet aren't detected, so the player is never punished before they're in frame.
- **`patinage`** (also "Pas de Patineur" — same reference file as `flappy`, different game entirely) reuses `flappy.js`'s exact ankle-zone step detector (`DALLE_Y_FRAC`, the `sideFresh` rising-edge pattern) but drops the external-bpm metronome: instead of "hit the lit tile in time or miss," speed is a momentum value that any valid alternating left/right step boosts (faster real alternation → bigger boost, tiered by measured interval) and continuous friction decays every frame (`speed -= speed*FRICTION*dt`) — deliberately never hits exactly zero on a missed beat, since the goal was "the glide should feel like ice," not a pass/fail rhythm gate. Steering reuses the *same* two-zone gesture with no new input: alternating sides keeps `turnBias` (and so the road curve) decaying toward neutral; two steps on the *same* side push `turnBias` toward that side — mirroring a real speed-skating crossover. Renders in genuine WebGL 3D via Three.js (see the shared-modules note above on why, not a 2D canvas re-skin): camera stays fixed at the origin, the road's forward motion is a scrolling grid *texture offset* (not moving geometry — cheap, perfectly seamless, no pop-in), while the handful of bonus tiles are individually positioned `Object3D`s whose `z` genuinely animates toward the camera and get collected by comparing their fixed lane to the live `lateralOffset`. `?exo=patinage` is accepted (read into `EXO_ID`) purely for parity with the reference file's multi-exercise convention — this game doesn't branch on it; don't build out a multi-exercise engine here to "use" it, that's a different architecture than one-folder-per-game.
- **`subway`** (runner) uses `render/perspective.js` for its scrolling ground.
- **`rooms`** (2-5 player co-op, star topology via `PeerRoom`) is **host-authoritative**: only the host (seat 0) runs the 5-level puzzle state machine; guests just render whatever state the host broadcasts, and every seat also broadcasts its own local gesture state (`handsUp`/`crouch`/`spread`/`lane`) plus a reduced 11-point landmark set (`REDUCED` in `room.js`) for rendering the other players' stick figures. Level conditions are generalized over `roster` (an arbitrary-length seat array) rather than hardcoded to two players — `allHave()` checks a gesture across every connected seat. Levels 1-4 (switches/press/mirror/bridge) are continuous "hold" mechanics. Level 5 is a discrete fire/bucket relay: the bucket auto-fills in `FIRE_FILL_TIME` (3s) at the water source, then passes seat-to-seat in roster order on a `handsUp` rising edge (`handsUpEdge`, not a hold) until it reaches the last seat, who throws it on the flame; a held bucket that times out (`FIRE_TURN_TIMEOUT`, 5s) with no pass spills and resets to the source rather than failing the room, consistent with the game's no-punishing-failure philosophy. `FIRE_THROWS_NEEDED` (3) successful relays extinguish the fire and complete the room. Player count (2-5) is chosen by the host in the lobby and drives both `PeerRoom.host(maxPlayers)` and the per-seat layout (`anchorFor(posInRoster, count)`).
- **`climb`** — the gripped hand's *rendered* position is deliberately clamped to a realistic arm length from the shoulder (`clampToArm`), decoupled from the *real* wrist position used for the underlying grab/climb physics — this was a deliberate fix for the arm otherwise visually stretching to the true (far) wrist position. Don't collapse these back into one value. `climbProgress` is a strict ratchet (`Math.max(climbProgress, computed)`) so pose noise or re-gripping an already-passed hold can never make the character descend — only upward and lateral movement are possible.
- **`combat`** — punch detection uses `elbowExtension()` (`gestures.js`): an `EdgeTrigger` per arm fires on the FRONT of a guard→extended transition, never on a static straight-arm state (a relaxed arm hanging at the side would otherwise false-trigger), and is further gated to only accept a punch when the wrist is above hip height. Play modes: **vs AI** (single player, local scoring only) and **1v1 online** via `PeerRoom.host(2)`/`join()` — reusing the same star-topology class as `rooms`, just degenerated to 2 seats. Each player picks exactly 3 of 5 bonuses (Punch, Shadow Dodge, Combo Master, Perfect Counter, Air Ace); the chosen set gates which prompt *types* the match generates for that player (`enabledTypes()`: `punch`/`combo` → punch prompts, `dodge`/`counter` → dodge prompts, `air` → air prompts), so every valid 3-of-5 pick always yields at least one prompt type. Each prompt cycles `telegraph` (a wind-up cue, shrinking with match elapsed time) → `window` (the scoring gesture must land) → optionally `counter` (a short follow-up window opened only after a successful dodge, if Perfect Counter is selected) → cooldown. **1v1 is a parallel score-attack duel, not a literal simultaneous clash**: both sides run their own independent local prompt schedule against their own chosen bonuses and periodically exchange `scoreUpdate`/`matchEnd` messages so each can render a live comparison bar and declare a winner by final score — this sidesteps trying to simulate a real physical exchange from pose data alone. Live 2-peer connection can't be verified in this sandbox (see the `PeerRoom.js` caveat above); tested via the same `?debug=1` hook + direct `tick(dt)` pattern as `rooms`.
- **`football`** (penalty shootout, vs AI only — no online mode) — a 5-round duel: each round the player shoots (`attackAim`→`attackResult`) then defends (`defendTelegraph`→`defendWindow`→`defendResult`). Aiming/diving both reuse `lateralZone` (left/center/right, shared with `combat`'s dodge); the kick itself is `kneeLift()` (`gestures.js` — exported since the start but, until this game, never actually consumed anywhere) through an `EdgeTrigger` calibrated purposely high (`0.05`/`0.12`) since a kick should read as a clearly more deliberate lift than a walking step. `resolveKeeperDive()` scales the AI keeper's save chance up with `round` (harder late) via a forced-correct-or-forced-wrong dice roll rather than literally reading the player's aim unfairly; `pickAiShotZone()` is lightly adaptive, half the time biased toward whichever zone `playerDiveCounts` shows the player has dived to least. Tied after the 5 regular rounds → `suddenDeath = true` and single-shot-each rounds repeat until the score differs after a round (real shootout rule), checked in `checkMatchEnd()`. **Layout gotcha discovered building this game, applies to every game**: `.stage` forces `aspect-ratio: 4/5` (portrait) on the shared 960×600 (16:10) canvas — composing across the full vertical range (e.g. a goal near `H*0.1` and a player near `H*0.9`) stretches into a huge dead-space gap once that portrait ratio is applied, worst on an actual phone. Keep scene anchors roughly within `H*0.2`–`H*0.7`, matching the range `combat` and `rooms` already use.

### Styling

`assets/css/main.css` is the one stylesheet for the landing page and every game shell (dark glassmorphism theme: `--bg-*`, `--accent*` custom properties). Game-specific visuals are drawn on `<canvas>`, not in CSS.

### Generated art assets

All games currently draw everything procedurally (canvas paths/gradients) — there are no image files in the repo. If asked to generate or integrate character/decor art, match the exact sizing the code already expects rather than guessing:

- **`subway` character** — SVG preferred (recolorable, tiny, crisp at any size) or PNG @2x. Draw at ~200×340px per pose (running/jump/crouch), **anchored feet-at-bottom-edge, horizontally centered** — the game code positions sprites by bottom-center, so that anchor is what makes drop-in replacement trivial. Transparent background. Style: flat neon silhouette matching the existing palette (body gradient `#e0f2fe`→`#7dd3fc`, limbs `#a78bfa`) — no fine detail, it needs to stay readable at speed.
- **`subway` coin** — PNG/WebP, 64×64, transparent, gold gradient `#fff7d6`→`#fbbf24`.
- **`subway` obstacles** — "block" (jump-over): 172×92, tint `#fb7185`. "bar" (duck-under): 172×52, tint `#fb923c`. Both PNG/WebP, transparent.
- **`subway` skyline** — PNG, 1440×260, must tile seamlessly left-to-right (it scrolls horizontally as a parallax strip), transparent background (the sky gradient stays in code, underneath).
- **`subway` road** — deliberately left procedural: it's drawn as a perspective-warped trapezoid via canvas path fills, not a flat `drawImage` rect, so texturing it with a raster image isn't practical without WebGL.
- Other games (`flappy`, `rooms`, `climb`, `rhythm`) have no asset spec yet — derive one the same way (read the game's draw functions for the exact on-screen size at z=0/near scale, add an anchor convention, double it for a crisp @2x source) before generating art for them.
